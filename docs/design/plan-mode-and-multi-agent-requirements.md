# CodePilot Plan 模式、子 Agent 与 Workflow 产品需求

状态：需求基线 v1  
形成日期：2026-08-26  
适用范围：CodePilot 后续 Plan 模式、子 Agent 和 Workflow 能力的产品设计与验收  
不包含：具体代码结构、接口、存储格式、调度算法和发布实现方案

对应落地方案：[Plan、Workflow 与多 Agent 可持续交付方案](../roadmap/plan-workflow-multi-agent-delivery-plan.md)

## 1. 文档目的

本文档定义 CodePilot 后续复杂任务处理能力的产品需求，统一 Plan、Workflow 和子 Agent 三个概念的职责、用户交互、能力边界和演进方向。

产品目标可以概括为：

> CodePilot 对简单任务直接完成；对复杂任务先征得用户同意进入 Plan 模式，形成可确认的方案；方案批准后，根据实际收益选择单 Agent、单 Agent Workflow 或多 Agent Workflow 执行。

本文档是需求层面的权威基线。后续技术设计和开发路线必须满足本文档，不得用实现便利改变这里定义的用户语义。

## 2. 核心概念

### 2.1 Plan

Plan 回答“要做什么、为什么这样做”。它既可以是面向后续实施的方案和确认边界，也可以是用户请求的规划类交付物；它不是内部思维过程，也不是文件修改或命令执行授权。

### 2.2 Workflow

Workflow 回答“任务按什么顺序、依赖关系如何推进”。它是计划执行时的结构化过程，可以由一个 Agent 执行，也可以包含多个 Agent。

### 2.3 子 Agent

子 Agent 回答“由谁完成某个具体任务”。它是由主 Agent 管理的受控执行单元，拥有明确目标、范围和完成标准，不是与用户并列的独立责任主体。

### 2.4 三者关系

Plan、Workflow 和多 Agent 是相互独立但可以组合的三个维度：

```text
Plan 获得批准
      ↓
选择执行策略
  ├─ 单 Agent 直接执行计划
  ├─ 单 Agent Workflow
  └─ 多 Agent Workflow
```

进入 Plan 不表示一定创建 Workflow，也不表示一定使用子 Agent。多 Agent 只有在能够显著改善质量、速度或上下文隔离时才应使用。

## 3. 产品原则

1. 用户显式输入 `/plan` 时，CodePilot 直接进入 Plan 模式。
2. CodePilot 主动建议进入 Plan 模式时，必须先获得用户确认。
3. Plan 模式必须提供可信的只读保证。
4. 只有实施型 Plan 获得用户批准后，CodePilot 才能退出 Plan 模式并开始实施；内容交付型 Plan 被接受后直接完成，不启动实施 Run。
5. Plan approval 不等于文件修改、命令执行或外部副作用授权。
6. 单 Agent 是默认执行方式，多 Agent 是有明确收益时的优化选择。
7. 主 Agent 始终是用户的唯一交互入口，并对所有子 Agent 的行为和最终结果负责。
8. Workflow 必须可见、可取消、可追踪，失败和阻塞不能被静默隐藏。
9. 重大范围变化、风险提升或资源扩张必须重新获得用户确认。
10. 用户不需要理解内部 Agent 架构，也能完成 Plan 确认、执行跟踪和异常处理。
11. 实施阶段必须能在空仓库中可靠创建首个文本文件及其父目录；不得要求模型通过平台相关的 `/dev/null` 补丁约定绕过文件工具能力缺口。

## 4. Plan 模式需求

### 4.1 显式进入

CodePilot 应支持以下入口：

```text
/plan
/plan <request>
```

- `/plan` 将输入区切换到当前任务的 Plan 状态，用户随后输入任务内容。
- `/plan <request>` 直接以 Plan 模式开始处理该请求。
- 用户显式输入 `/plan` 本身已经构成进入 Plan 模式的确认，不应再次要求批准 `EnterPlanMode`。
- Plan 状态只作用于当前任务。任务完成、取消或明确退出后，界面恢复普通输入状态，除非用户另外选择长期偏好。
- 界面必须持续显示当前处于 Plan 模式，避免用户误以为 CodePilot 正在修改代码。

### 4.2 Agent 主动建议进入

用户没有显式输入 `/plan` 时，CodePilot 可以在判断任务足够复杂后主动调用 `EnterPlanMode`。

该动作必须先展示简洁、可理解的建议理由，并等待用户确认。用户至少可以选择：

- 进入 Plan 模式。
- 继续直接处理。
- 取消当前任务。

用户拒绝进入 Plan 后，CodePilot 不得把拒绝解释为拒绝原任务。同一任务在没有发现实质性新信息时，不应重复请求进入 Plan。

### 4.3 建议 Plan 的判断依据

CodePilot 应综合以下因素判断是否建议 Plan：

- 目标、范围或验收条件存在明显歧义。
- 涉及多个模块、多个系统或公共接口。
- 实施步骤存在重要先后依赖。
- 存在多种可行方案，需要用户参与取舍。
- 涉及数据迁移、兼容性、安全、权限或不可逆操作。
- 修改面较大，失败后的回退成本较高。
- 验证链路复杂或需要多个环境。
- 适合拆分为多个相对独立的工作流。
- 执行中发现实际复杂度明显超过最初判断。

简单修复、明确的小范围改动和纯解释类问题不应频繁触发 Plan 建议。判断目标是降低返工和风险，而不是增加仪式感。

### 4.4 只读探索

进入 Plan 模式后，CodePilot 可以：

- 读取、搜索和分析代码。
- 查看项目结构、依赖和配置关系。
- 查看 Git 状态、差异和历史等只读信息。
- 向用户提出完成方案所必需的澄清问题。
- 在有明确收益时使用只读子 Agent 探索不同模块。
- 形成和修订实施计划。

Plan 模式禁止：

- 创建、修改、移动或删除文件。
- 执行可能改变工作区、系统或外部服务状态的命令。
- 修改 Git 状态或向远端写入数据。
- 发送外部消息或改变第三方系统状态。
- 以“验证方案”为理由绕过只读边界。

是否产生副作用应以行为结果判断，不能只依据工具或命令名称。

Plan 模式不能因为当前会话绑定了 Worktree 就默认读取仓库。只有计划结论确实依赖当前项目事实时，才应使用文件、Git 或项目 guidance；普通问答、内容策划、活动安排等与仓库无关的规划请求应以零工作区工具完成。

#### 4.4.1 需求澄清

当缺失信息或方案选择会实质改变目标、范围、架构、风险、兼容性、成本或最终交付结果，并且无法从现有上下文或只读证据确认时，CodePilot 应暂停 Planning 并请求用户选择。

- 每次中断集中提出当前已知的 1～3 个相关且聚焦的问题，避免用户回答一题后才暴露原本已知的下一题。
- 每个问题提供 2～4 个候选项。候选项互斥时使用单选；多个候选项可以组合时使用多选，不得强行把组合需求降级成单选。
- 单选可以标记一个推荐项，多选可以标记推荐组合，并简述各选项的影响或取舍。模型漏标或重复标记推荐项时，产品应安全规范化展示，不得把可恢复的结构化输出抖动作为用户可见失败。
- 始终提供“其他”入口，允许用户补充自由文本；进入“其他”输入后应在当前澄清卡片内实时显示输入内容和提交方式，不应保留一个看似无响应的选项列表。
- 能从项目中确认的事实不得反问用户；低影响、可撤销的实现细节应采用明确假设，避免把 Plan 变成问卷。
- 只有用户回答或新证据进一步暴露了新的重大歧义时，才应发起后续澄清中断；Plan 不限制澄清轮次，但每次中断必须保持有界。
- 用户回答后仍处于 Planning，只能继续只读探索和计划编写；回答不构成 Plan approval、权限批准或执行授权。
- 澄清请求和回答必须持久化，重启或 Provider 瞬时失败后不得丢失，也不得重复应用到其他问题或 Plan 版本。

### 4.5 计划内容

计划至少应包含：

- 目标与预期结果。
- 通过只读探索获得的关键现状。
- 本次任务范围和明确不做的内容。
- 关键假设、限制和待确认事项。
- 推荐方案及主要取舍。
- 有顺序和依赖关系的实施步骤。
- 每一步预计涉及的模块或文件范围。
- 风险、兼容性和必要的回退考虑。
- 验证方法和最终完成标准。
- 推荐执行方式：单 Agent、单 Agent Workflow 或多 Agent Workflow。
- 如果推荐多 Agent，说明拆分依据、主要工作流和预期收益。
- 计划是否依赖当前工作区，以及它是“批准后实施”还是“计划本身即交付物”。

计划应清晰、可操作、可验证，不应包含模型内部思维过程，也不应伪造未经探索确认的事实。

### 4.6 计划确认与退出

计划完成后，CodePilot 通过 `ExitPlanMode` 发起计划确认。调用该动作本身不能立即恢复执行能力；必须先向用户展示计划并等待决定。

对于批准后需要实施的 Plan，用户至少可以：

- 批准计划并开始实施。
- 提交反馈并要求修改计划。
- 取消当前任务。

对于计划本身就是交付物的 Plan，用户至少可以：

- 接受计划并完成当前任务，不启动新的执行 Run。
- 提交反馈并要求修改计划。
- 取消当前任务。

用户要求修改时，CodePilot 继续留在 Plan 模式，根据反馈更新方案并再次提交确认。每次提交都应让用户能够识别计划发生了哪些重要变化。

只有用户批准后，CodePilot 才退出 Plan 模式并恢复实施所需的能力。

### 4.7 Plan approval 的边界

批准计划表示用户同意：

- 按计划描述的目标、范围和总体方案推进。
- 使用计划中明确展示的执行方式。
- 当计划明确展示子 Agent 或 Workflow 分工时，按该安排组织执行。

批准计划不表示用户同意：

- 任意修改未展示的范围。
- 自动批准所有文件变更或命令。
- 访问敏感数据或外部系统。
- 无限制增加 Agent 数量、运行时间或资源消耗。
- 忽略执行中发现的新风险。

具体副作用仍遵循 CodePilot 的权限和审批规则。

### 4.8 执行偏差与重新规划

计划批准后，CodePilot 可以在不改变目标和风险的前提下进行轻微实现调整，但出现以下情况时必须暂停并重新规划：

- 关键假设不成立或原方案不可行。
- 需要明显扩大任务或文件范围。
- 需要新增高风险、敏感或不可逆操作。
- 工作区变化使原计划失效。
- 验证结果证明计划需要实质性改变。
- 需要将原定单 Agent 执行升级为明显更大或成本更高的多 Agent Workflow。

重新规划后，应再次向用户展示重要变化并获得确认。

## 5. 子 Agent 需求

### 5.1 定位与责任

- 主 Agent 是用户的唯一责任主体和默认交互入口。
- 主 Agent 负责拆分任务、选择执行方式、分配工作、处理依赖、验证结果和汇总交付。
- 每个子 Agent 必须有明确的目标、范围、输入、输出和完成标准。
- 子 Agent 不能自行扩大任务范围、改变用户目标或创建不受控制的下级任务。
- 子 Agent 的权限和可访问范围不能超过父任务和用户已授予的边界。
- 子 Agent 失败、超时或产生冲突时，主 Agent 必须说明影响并采取明确的后续策略。

### 5.2 初始角色

产品初期应优先支持职责稳定的角色：

- `Explore`：只读探索代码、依赖和影响范围。
- `Implement`：完成一个边界明确的修改任务。
- `Validate`：执行验证、测试或检查。
- `Review`：根据计划和证据检查结果。
- `Integrate`：汇总多个任务结果并处理衔接问题。

角色用于表达职责和能力边界，不是允许模型自由创造无限人格。

### 5.3 使用多 Agent 的条件

适合使用多 Agent：

- 存在多个相互独立的探索方向。
- 多个模块可以并行分析或实现。
- 任务能够按清晰边界拆分，汇总成本可控。
- 实现与验证适合由不同角色交叉检查。
- 单 Agent 上下文过大，拆分有助于保持准确性。

不适合使用多 Agent：

- 简单单文件或小范围修改。
- 步骤具有强顺序依赖且任务较短。
- 多个 Agent 会频繁修改相同范围。
- 拆分、协调和汇总成本高于预期收益。
- 只是为了展示多 Agent 能力。

单 Agent 应作为默认选择。Agent 数量应由任务需要决定，而不是越多越好。

### 5.4 Plan 阶段的子 Agent

Plan 模式可以选择使用只读子 Agent 并行探索，但不是每次 Plan 都必须使用。

- 使用原因和当前探索任务应对用户可见。
- 所有子 Agent 继续受到 Plan 模式只读边界约束。
- 主 Agent 必须验证和汇总子 Agent 的关键发现。
- 大规模增加子 Agent 或资源消耗时，应遵循可见的产品限制或额外确认。

## 6. Workflow 需求

### 6.1 Workflow 的适用范围

Workflow 用于结构化管理执行过程。它既可以由单 Agent 完成，也可以把不同节点分配给多个子 Agent。

每个 Workflow 至少应表达：

- 任务节点及其目标。
- 节点之间的依赖关系。
- 可串行或并行的关系。
- 每个节点的责任角色和工作范围。
- 节点完成标准和验证要求。
- 当前状态、进度和阻塞原因。
- 失败后的重试、降级、重新规划或终止选择。
- 最终汇总和整体验证步骤。

### 6.2 执行策略选择

Plan 批准后，应根据计划特点选择以下一种执行方式：

#### 单 Agent 直接执行计划

适用于范围集中、依赖紧密且不需要复杂进度管理的任务。这是默认方式。

#### 单 Agent Workflow

适用于步骤较多、需要依赖跟踪、恢复或清晰进度展示，但拆分给多个 Agent 没有明显收益的任务。

#### 多 Agent Workflow

适用于存在独立工作流、并行收益或明确角色分工的任务。

计划中应在用户批准前展示推荐执行方式。用户可以要求改为单 Agent，或者通过计划反馈调整分工。

### 6.3 多 Agent Workflow 的编排要求

- 主 Agent 负责全局目标、依赖和最终质量。
- 只有依赖已经满足的节点才能开始。
- 并行任务必须具有明确的范围边界。
- 多个写任务不能互相覆盖，也不能破坏用户已有修改。
- 子 Agent 输出应包含结论、变更、证据、验证结果和未解决问题。
- 主 Agent 不能仅因为子 Agent 声称完成就视为整体完成。
- Workflow 完成前必须进行统一验证和最终 Review。

### 6.4 动态调整

执行中可以在批准范围内调整节点分配、重试失败任务或降级为单 Agent，但以下变化必须重新向用户确认：

- 明显扩大任务目标或工作范围。
- 显著增加 Agent 数量、执行成本或预计时间。
- 引入计划中未展示的高风险操作。
- 改变用户已经确认的关键方案。

## 7. 用户体验需求

### 7.1 状态可见性

用户应能清楚识别当前状态：

- 普通处理。
- 等待确认进入 Plan。
- Plan 只读探索。
- 等待计划批准。
- 单 Agent 执行。
- Workflow 执行。
- 等待权限或其他用户决定。
- 已暂停、取消、失败或完成。

### 7.2 Plan 展示

计划应以易于浏览的结构展示，而不是淹没在普通对话文本中。用户应能够快速看到：

- 目标和范围。
- 关键步骤和依赖。
- 风险和待确认项。
- 验证方式。
- 推荐执行方式。
- 如果使用多 Agent，主要分工和并行关系。

### 7.3 Workflow 展示

多 Agent 不应把界面变成内部日志流。默认视图应展示：

- 总体进度。
- 正在进行、已完成和受阻的任务。
- 当前运行的 Agent 数量和职责。
- 等待用户处理的决定。
- 失败原因及下一步选择。

用户可以按需展开节点详情，但不必阅读所有子 Agent 对话。

### 7.4 用户控制

用户应能够：

- 批准、修改或取消计划。
- 拒绝 Agent 建议的 Plan 模式并继续原任务。
- 要求使用单 Agent 执行。
- 暂停或取消活动 Workflow。
- 查看某个任务节点的结果和证据。
- 了解执行是否偏离批准计划。
- 在失败时选择重试、降级、重新规划或终止。

取消应尽快停止尚未完成的工作，并向用户说明已经完成、未完成和可能需要检查的部分。

## 8. 安全、权限与信任需求

1. Plan 模式的只读边界必须由产品能力保证，不能依赖模型自觉。
2. Plan、仓库内容、子 Agent 输出和 Workflow 结果均不能扩大权限。
3. Plan approval 与具体副作用审批保持分离。
4. 子 Agent 继承的是受限任务能力，而不是父 Agent 的全部隐式权限。
5. 多 Agent 并行执行不能覆盖用户已有修改或其他 Agent 的未合并工作。
6. 敏感信息不能因为进入 Plan、创建子 Agent 或汇总结果而扩大暴露范围。
7. 用户取消、进程退出或任务恢复时，不能重复执行已经发生的不可安全重放操作。
8. 对 `create_file` 选择“本会话允许”后，授权应覆盖当前会话、当前工作区内后续通过同一专用工具发起的安全新建操作，而不是只覆盖首次选择的单一路径；该授权不得扩展到编辑、覆盖、命令执行、敏感路径或其他工具。
9. 每次文件创建仍必须独立执行路径边界、敏感路径、秘密内容、目标不存在和并发状态校验；会话授权只减少重复确认，不能跳过安全检查。

## 9. 异常与恢复需求

发生中断、崩溃或重新打开会话后，CodePilot 应能够准确恢复到用户可理解的状态，包括：

- 等待确认进入 Plan。
- 正在 Plan 只读探索。
- 等待计划批准或修改。
- 已批准、尚未开始实施。
- Workflow 执行中或部分完成。
- 等待权限决定。
- 子 Agent 失败或节点受阻。

恢复后不得：

- 未经确认自动进入或退出 Plan。
- 重复执行已经完成的副作用。
- 丢失用户批准的计划版本。
- 将旧计划批准应用到新版本。
- 隐藏可能存在的部分完成状态。

## 10. 非目标

第一阶段不以以下能力为目标：

- 每个任务都强制 Plan。
- 每个 Plan 都强制创建 Workflow。
- 每个 Workflow 都强制使用多个 Agent。
- 让用户分别管理和聊天控制每个子 Agent。
- 允许模型无限创建 Agent、无限并发或无限消耗资源。
- 让 Plan approval 替代权限审批。
- 在未经确认的情况下自动扩大任务范围。
- 跨机器分布式 Agent 或远程执行集群。
- 以展示内部思维过程作为计划质量的证明。

## 11. 验收标准

### 11.1 Plan

- `/plan` 可以明确进入当前任务的 Plan 模式。
- Agent 主动调用 `EnterPlanMode` 时，未经用户确认不会进入 Plan。
- Plan 模式下不能产生工作区、系统或外部服务副作用。
- 计划必须包含目标、范围、步骤、风险和验证方式。
- 用户可以批准、要求修改或取消计划。
- 关键歧义可以通过单次 1～3 题、按问题语义选择单选或多选、并带候选项和自由文本“其他”的结构化澄清交互解决；“其他”输入在卡片内实时可见。全部回答后仍保持只读 Planning，后续仍可按需再次澄清。
- 与工作区无关的 Plan 不读取仓库文件或 Git 状态。
- 内容交付型 Plan 被接受后直接完成，不会创建实施 Run 或产生第二次无意义的 Provider 执行请求。
- 实施型 Plan 在空仓库中可以通过受权限控制的专用文件创建能力落地首个文件及父目录，不依赖手写 `/dev/null` 补丁。
- `create_file` 的“本会话允许”在当前会话内对后续安全新建文件生效，不再逐文件重复询问，同时不授权覆盖已有文件或调用其他写工具。
- TUI 将连续的 `create_file` 调用聚合为一个可选择的活动块，并以目录树持续展示已创建文件；底层逐文件结果和审计记录保持不变。
- 宽屏 TUI 展开带 Diff 的工具活动时，应在文件列表右侧显示独立的变更面板：展示旧/新行号和 unified diff 片段，删除行使用红色、增加行使用绿色、hunk 定位使用辅助色，并可在面板内滚动；窄屏自动回退到纵向内联 Diff。
- 用户在生成中、权限审批、Plan 审批、澄清或恢复界面选中文本后仍可复制；仅在没有选区时，`Ctrl+C` 才保留取消活动任务或退出的语义。
- 未批准 `ExitPlanMode` 时不能恢复实施能力。
- 计划修改后，旧批准不能作用于新计划。
- 执行发生重大偏离时会暂停并重新确认。

### 11.2 子 Agent 与 Workflow

- Plan 后可以选择单 Agent 执行，不会自动进入多 Agent。
- 计划能够展示推荐执行方式和多 Agent 分工。
- 用户可以要求使用单 Agent。
- 子 Agent 的任务范围、状态和结果可追踪。
- Workflow 正确表达依赖、并行、阻塞和完成状态。
- 子 Agent 失败不会被静默视为整体成功。
- 取消 Workflow 会停止尚未完成的子任务并报告部分结果。
- 多 Agent 完成后由主 Agent 统一验证和交付。

### 11.3 用户信任

- Plan 模式下意外副作用数量为零。
- 未经确认自动进入 Plan 或退出 Plan 的次数为零。
- 未展示的重大范围扩大数量为零。
- 用户能够从界面判断当前模式、执行策略和等待事项。
- “本会话允许”的实际授权范围与按钮文案一致，批量文件创建不会造成重复授权疲劳或连续工具卡片刷屏。

## 12. 效果指标

Plan 重点关注：

- Plan 建议接受率和拒绝率。
- 简单任务被不必要建议 Plan 的比例。
- 复杂任务因未规划导致的返工率。
- 首版计划直接获批、修订后获批和取消的比例。
- 批准后发生重大重新规划的比例。
- Plan 带来的额外时间和资源成本。

多 Agent 重点关注：

- 相比单 Agent 的完成质量和成功率变化。
- 实际并行带来的时间收益。
- 子 Agent 协调、冲突和返工成本。
- 任务拆分后遗漏需求的比例。
- 单任务的资源放大倍数。
- 用户主动要求退回单 Agent 的比例。

指标用于判断功能是否真正改善任务结果，不用于推动更多 Plan 或更多 Agent 使用量。

## 13. 产品演进方向

建议按用户价值和风险逐步完善：

1. 显式 `/plan`、可信只读探索、计划展示和批准执行。
2. `EnterPlanMode` 主动建议及用户确认。
3. 计划修订、取消、偏差提示和重新规划。
4. Workflow 进度展示和单 Agent Workflow。
5. 串行子 Agent 与主 Agent 统一汇总。
6. 多个只读子 Agent 并行探索。
7. 基于批准计划的多 Agent 实施、集成和统一验证。
8. 冲突处理、失败降级和动态重规划。
9. 在上述体验稳定后，再评估后台任务、跨会话运行和更高级的资源策略。

## 14. 需求结论

CodePilot 后续应坚持以下产品关系：

> Plan 模式是用户控制复杂任务的决策边界；Workflow 是批准方案的推进方式；子 Agent 是 Workflow 内部的受控执行资源。

三者可以组合，但没有必然绑定。Plan 后默认仍然可以由单 Agent 执行；只有在任务可有效拆分且收益明确时，才采用多 Agent Workflow。
