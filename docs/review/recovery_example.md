# CodePilot Agent 崩溃恢复的现实意义

## 📌 完整场景：处理 GitHub Issue

### **初始任务**
用户要求 Agent 完成：**根据 GitHub Issue 自动生成修复代码并创建 PR**

任务分解为 5 个工具调用：
```
Tool #1: 获取 Issue 详情        (get_issue)
Tool #2: 分析代码问题          (analyze_code)  
Tool #3: 生成修复代码          (generate_fix)  
Tool #4: 提交到 Git 仓库       (git_commit)
Tool #5: 创建 Pull Request     (create_pr)
```

---

## ⚠️ 场景：系统崩溃在 Tool #3

```
时间线：
─────────────────────────────────────
09:00 ✅ Tool #1 完成 → 拉取了 Issue 数据到数据库
09:15 ✅ Tool #2 完成 → 分析了代码，报告了问题
09:30 ⏳ Tool #3 执行中... → 正在生成修复代码
       ❌ CRASH! 系统崩溃了
─────────────────────────────────────
```

此时的状态：
- ✅ Issue 数据：已获取（数据库中存在）
- ✅ 代码分析结果：已生成（日志中保存）
- ⏳ 修复代码：**生成中** → 不清楚是否完成
- ❌ Git 提交：未开始
- ❌ PR 创建：未开始

---

## ❌ 没有恢复机制的后果

重启后系统从头开始：

```
重启后执行 (09:35)：

Tool #1: 获取 Issue 详情 (再次执行)
  └─ 问题1: GitHub API 再次调用 (浪费配额和时间)
  └─ 问题2: 数据库中可能有重复数据
  └─ 耗时: ~30秒

Tool #2: 分析代码 (再次执行)
  └─ 问题1: 重复分析，浪费 AI 算力
  └─ 问题2: 生成新的分析报告 (可能内容略有不同)
  └─ 耗时: ~2分钟

Tool #3: 生成修复代码 (再次执行)
  └─ 问题1: 完全重新生成
  └─ 问题2: 这次可能生成了不同的代码
  └─ 耗时: ~5分钟

Tool #4: 提交到 Git
  └─ 结果: 提交了新的代码版本 (与之前的不同!)

Tool #5: 创建 PR
  └─ 结果: 如果之前的代码已经被手动提交过...
           现在创建了新的 PR (重复!)

总耗时: ~7-8 分钟 (白白浪费!)
状态: 混乱 (可能有多个版本的代码和 PR)
```

---

## ✅ 有恢复机制的优势

系统能够从断点继续：

```
恢复流程 (09:35)：

1️⃣ 读取持久化日志
   └─ 查看 Session 记录
   └─ 发现: Tool #1-2 已完成，Tool #3 未完成

2️⃣ 构建恢复计划 (RecoveryPlan)
   ┌─ Tool #1: ✅ 完成 (跳过)
   ├─ Tool #2: ✅ 完成 (跳过)
   ├─ Tool #3: ⏳ 待处理
   │            └─ ReplayPolicy: Idempotent (使用原 idempotency_key)
   │            └─ 需要决策: 重试、确认已完成、还是标记失败?
   ├─ Tool #4: ⏹️  待执行
   └─ Tool #5: ⏹️  待执行

3️⃣ 应用恢复决策 (基于 ReplayPolicy)
   如果 Tool #3 是 Idempotent:
   └─ 系统使用 idempotency_key 重新执行
   └─ 服务器检测到重复请求，返回之前的结果
   └─ 不会产生重复的修复代码

4️⃣ 继续执行
   Tool #3: 恢复之前的结果 (幂等)
   Tool #4: 提交代码 (只有一个版本)
   Tool #5: 创建 PR (只有一个 PR)

总耗时: ~5分钟 (只需完成 Tool #3-5)
节省: ~2-3 分钟时间，且数据一致
```

## 🔑 核心代码流程

```go
// 1. 加载会话快照
snapshot, _ := r.sessions.Load(ctx, sessionID)

// 2. 构建恢复计划 (分析哪些任务完成，哪些未完成)
plan := agentsession.BuildRecoveryPlan(snapshot)
// plan.Actions = [
//   {ID: "tool-1", Status: "completed", Kind: "ReconcileTool"},
//   {ID: "tool-2", Status: "completed", Kind: "ReconcileTool"},
//   {ID: "tool-3", Status: "pending", Kind: "RecoveryRetryTool"}, ← 需要处理
//   ...
// ]

// 3. 执行恢复 (处理 Tool #3)
result := r.Recover(ctx, RecoverRequest{
    SessionID:    sessionID,
    ActionID:     "tool-3",
    Decision:     RecoveryRetry,  // 选择重试
    ContinueRun:  true,           // 之后继续执行后面的步骤
    Automatic:    true,           // 自动恢复 (安全的 Idempotent 工具)
    ...
})

// 4. 结果
// - Tool #3 使用 idempotency_key 重新执行 (幂等，获得相同结果)
// - Tool #4 继续执行
// - Tool #5 继续执行
// - 单一、一致的最终状态
```

## 🎯 恢复机制解决的问题

| 问题 | 无恢复机制 | 有恢复机制 |
|------|----------|----------|
| **时间浪费** | 重做所有已完成的步骤 | 从断点继续 |
| **API 配额** | 重复调用 GitHub API | 调用减少 50-70% |
| **AI 成本** | 重复调用 LLM 生成代码 | 仅恢复未完成部分 |
| **数据一致性** | 可能产生多个版本 | 幂等保证唯一版本 |
| **用户体验** | 不可预测，需要手动介入 | 自动恢复，透明可靠 |
| **副作用** | 可能创建重复的 PR/提交 | 检测重复，安全执行 |

---

## 💡 ReplayPolicy 的关键作用

```go
// Tool 的重放策略决定了能否安全地重试

ReplaySafe       // 无副作用的操作 (如: 读取文件)
                 // 可以无限重试

ReplayIdempotent // 有副作用但幂等 (如: 创建带 Key 的资源)
                 // 使用 IdempotencyKey 防止重复
                 // 服务器对同 Key 请求返回相同结果

ReplayNever      // 有不可逆副作用 (如: 删除、发送通知)
                 // 禁止重试，需要用户决策
```

## 📊 性能对比

假设：
- Tool #1-2 各耗时 2 分钟
- Tool #3 耗时 5 分钟
- Tool #4-5 各耗时 1 分钟

```
无恢复机制:
  重新执行 Tool #1   (2分钟)
  重新执行 Tool #2   (2分钟)
  重新执行 Tool #3   (5分钟) ← 可能内容不同！
  执行 Tool #4       (1分钟)
  执行 Tool #5       (1分钟)
  ─────────────────
  总耗时: 11分钟 ❌ (白白浪费 4 分钟)

有恢复机制:
  跳过 Tool #1 (已完成)
  跳过 Tool #2 (已完成)
  恢复 Tool #3       (5分钟, 幂等) ← 相同内容
  执行 Tool #4       (1分钟)
  执行 Tool #5       (1分钟)
  ─────────────────
  总耗时: 7分钟 ✅ (节省 4 分钟，节率 36%)
```

## 总结

**恢复机制的核心价值：**

1. **⏱️ 时间效率** - 避免重做已完成的工作
2. **💰 成本节省** - 减少 API 调用和 AI 推理成本
3. **🎯 数据一致** - 通过幂等性保证单一真实版本
4. **🛡️ 可靠性** - 自动从崩溃中恢复，无需手动干预
5. **🔄 透明度** - 清晰的恢复决策流程，用户可控

这就是为什么在分布式系统和长流程任务中，**崩溃恢复机制是必需的**。
